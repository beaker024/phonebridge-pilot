# Build and environment recovery

## Existing cloud environment

Initial inventory found no Gradle installation/cache, Android `android.jar`, SDK
build tools, APK signer or downloaded reference repositories. Python MCP/httpx and
the JVM compiler module were installed. The `javac` executable is absent, but
`java --module jdk.compiler/com.sun.tools.javac.Main` works for pure-Java tests.
Android source syntax parsing is possible; Android symbol/type checking is not.

The network policy file describes unrestricted HTTP through `http://proxy:8080`.
Earlier shell attempts failed because this proxy was unreachable. The supported
environment status tool now reports a connected/running environment with enforced
unrestricted policy, but this is **not evidence that the proxy is healthy**. No
shell network retest was made in this turn. The separate documentation connector
could retrieve some public source pages; it cannot supply SDK ZIPs or a complete
repository/dependency cache to the shell filesystem.

The cloud runtime skill states that connectivity goes through the supplied sidecar
and that configuration changes require the environment configuration workflow.
The installed environment tool is read-only; there is no callable sidecar restart
or configuration-write operation. Editing the policy file, unsetting the proxy,
trying a different route, or suppressing TLS verification would not be a supported
repair, and was not attempted.

**Supported user-side recovery:** use the ChatGPT/Codex cloud environment controls
to restart/recreate or detach/reattach this environment (preserve/download the source
bundle first). Exact labels depend on the host UI and are not exposed to this agent.
If no restart control is available, report the broken proxy to platform support.
Opening policy already says unrestricted; changing a host allowlist alone will not
repair an unreachable proxy. A healthy environment would let Codex fetch/build the
remaining dependencies directly without involving a PC.

## External resources actually needed for an APK

1. Gradle **8.13** distribution from the official Gradle distribution service.
2. Android SDK **platform 36** (`android.jar` and platform resources).
3. Android SDK **build-tools 36.0.0**, including AAPT2, D8 and APK signing tools.
4. Google Maven/Maven Central dependencies for Android Gradle Plugin **8.13.2** and
   its transitive dependencies. A Gradle ZIP and `android.jar` alone are not enough.
5. A complete working JDK 17+ toolchain if the restored environment's bundled runtime
   is not recognized by Gradle. The free CI path installs Temurin 17 automatically.

Official sources: [Android SDK](https://developer.android.com/studio#command-tools),
[Gradle distributions](https://services.gradle.org/distributions/),
[Android Gradle Plugin releases](https://developer.android.com/build/releases/gradle-plugin).
All are development dependencies, not paid runtime services. No OpenAI API credentials
or GitHub token should be uploaded into this conversation to fetch them.

You can provide SDK/build archives or a populated dependency cache by downloading
them on your Android phone and attaching them here. A source/project archive for
the selected upstream project can also be attached. They need to be split to the
upload tool's 32 MiB-per-file limit where necessary. However, gathering every Maven
dependency manually is inconvenient; the free phone-triggered CI build is simpler
than making you assemble an offline SDK cache.

## Free CI path

`.github/workflows/build.yml` uses a standard `ubuntu-24.04` public-repository runner,
Java 17, Gradle 8.13 and SDK 36. It tests the bridge/native guard, compiles both APKs,
runs Android lint and verifies the APK signatures. No Play account, paid runner,
Codespace, domain, hosting, tunnel account or model API is involved.

It is **not yet run**, because this workspace has no writable/authenticated GitHub
connection and cannot download build dependencies. The source publishing helper is
for the user's phone; it has not been executed. Its use makes source public, not
device data or credentials. Build artifacts last one day to keep storage small.

APKs use Android's development signing configuration with `debuggable false` in
the Android manifests generated by the debug variant. Do not rely on that ephemeral
CI debug key as a long-term update identity: it can change between builds, requiring
uninstall/reinstall/re-pair. A future personal release should use a user-held signing
key stored privately, never committed or shared in ChatGPT. No signing key is needed
from the user to attempt this first pilot build.

## Phone-local compilation fallback

Termux can run Java/Gradle tooling, but Android's desktop SDK binaries are not all
Android/aarch64 executables. Phone-native AAPT2 and any ARM64 build dependencies
must be selected explicitly, not assumed from a Linux SDK ZIP. AndroidIDE-derived
toolchains/community ARM64 builds require a current provenance/compatibility audit;
none is claimed as verified here. Same-device wireless ADB is technically another
testing route, but is unnecessary for this Accessibility design and would broaden
privileges. The cloud CI path avoids all of these local compilation dependencies.
